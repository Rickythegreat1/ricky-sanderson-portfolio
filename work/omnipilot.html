Define the task, scope and stopping point.

A request like “review this project” hides several decisions: what the assistant can access, which steps it will take, when it should stop and what counts as done.

My browser-assistant research covered task progress, expected-state checks, memory and error recovery. The interface brings the task, access scope and next review point into one workflow.

This is an independent project based on my research and specifications.

Turn the research into requirements.

I wrote the research and product documents, which explored several browser architectures and model choices. The current build uses a defined implementation, with earlier designs archived separately.

01 / The workflow

Review the ordered workflow.

  2. 02Review the draft

    Check order, target and scope.

  3. 03Approve an action

    Permit this step once.

  4. 04Inspect the result

    Compare evidence with intent.

  5. 05Retain or schedule

    Choose what happens next.

Each stage has a separate review or retention decision.

Draft the task before running it.

The Codex sub-harness is the workspace for this sequence. A coding request becomes a typed task with an explicit workspace and sandbox choice. The ordered editor exposes the task before a run. Connecting the runtime is a separate step from approving work.

Browser recordings offer another entry point. Captured clicks and targets can become a workflow, while typed values are omitted and supplied during review. That keeps capture from quietly collecting sensitive input.

02 / Control & memory

Separate access from action approval.

Scope

Approve the specific action.

Browser origins, workspace access and native runtime connection are separate concerns. Consequential steps require one-time approval tied to the workflow revision and action.

Recovery

Check interrupted actions before retrying.

A durable checkpoint precedes dispatch. If a write may have happened before an interruption, the workflow blocks replay until the observed result is reconciled.

Completion

Inspect the result before accepting it.

Codex completion is not enough to prove the task was done correctly. The interface asks someone to inspect the actual result. Schedules create work due for review, not unattended approval.

Separate recovery state from history.

My research distinguished page context, task state, session memory and an action log. The current implementation separates recovery storage from optional completed history. Recovery requires storing state before a task has finished.

The memory view makes retention opt-in and exposes local purge. It also says what purge cannot do: remove copies held by Codex or the model provider. The sandbox limits writes and tool networking, not every filesystem read, so real work requires an appropriately isolated environment.

04 / Evidence & limits

Testing and remaining work.

Changes made during testing.

The editor gained visual step creation and reordering, and unsaved fields now survive stage changes. Test-driven repairs also addressed cancellation races, stale approvals and interrupted actions that could otherwise be dispatched twice. The design-library controls and archive paths were repaired and retested.

The result is a development build with explicit approval and recovery states. Adoption, time savings and task-success rates have not been measured.

Automated checks
The recorded suite passed 160 Node tests and 52 JavaScript syntax checks. These include mocked platform boundaries, so they do not prove a complete installed integration.
Actual browser checks
The production DOM executor passed 12 fixture checks. A browser pass completed 22 state checks before the latest motion changes. The current motion paths have been observed in the browser; a full regression pass is still pending.
Real runtime handshake
The installed Codex process initialized and returned its account status. It was unauthenticated. No model task or sign-in was performed.
Still to establish
Adapter source covers Windows, macOS 14+ and explicit Linux X11 sessions. macOS compilation, installed-extension/native-host acceptance and authenticated Codex work remain unverified. Wayland control is not implemented. No desktop platform is claimed accepted.
